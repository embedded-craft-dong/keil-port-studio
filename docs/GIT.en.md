# Git version control

[简体中文](GIT.zh-CN.md) · [GUI guide](GUI.en.md)

Use **Git** in the footer. It starts from the selected Keil project and resolves
the enclosing repository. The displayed root and operation scope may therefore
include other projects: verify the path. Use **Other project** to change folders.
After manually editing a path, refresh before performing an operation.

## First use

Git 2.23+ is required (`git restore` is used for unstaging); prefer a supported official build.

1. If Git is missing, choose **Install Git** and confirm. On Windows with winget,
   this launches an interactive Git.Git installation; otherwise it opens the official
   download page. You handle installer options, agreements and administrator prompts.
   The tool does not silently elevate privileges or disable security software.
2. Use **Refresh / detect** after installation. Standard installation folders are
   checked even before PATH refreshes. A launched installer is not reported as a
   successful installation. For custom locations, add Git to PATH and restart.
3. **Initialize** creates repository metadata, without automatically committing.
   It refuses to create a nested repository inside an existing one.
4. **Identity** stores a name/email in this repository only, not global settings.
   This identity will be visible in commits.
5. Review `.gitignore` (basic rules can be generated by Project tools). Never stage
   passwords, tokens, certificates or unnecessary build outputs. Git is not a complete backup.

Official instructions: [Git for Windows](https://git-scm.com/install/windows)
and [Microsoft winget install](https://learn.microsoft.com/en-us/windows/package-manager/winget/install).

## Commit workflow

1. Refresh and inspect changes. XY represents index/worktree status; `??` is untracked.
2. Ctrl/Shift-select rows, then **Stage selected**. **Unstage selected** keeps working files.
3. **View diff** shows staged and unstaged text differences. Binary files have no
   visual diff. Untracked content is absent from `git diff` until staged: inspect it yourself.
4. Enter a meaningful message and **Commit staged**. Confirmation commits the
   **entire index**, including files staged earlier by other tools, not just selected
   rows. There is no automatic `git add .`.
5. **History** shows the latest 30 commits.

## Remote operations

Set a remote name (usually `origin`) and HTTPS/SSH URL or local repository path.
Never embed passwords/tokens. Complete initial authentication using Git/Git Credential
Manager; this panel does not handle login or store credentials. Open trusted repositories
only: Git hooks, filters and credential helpers may execute code.

Choose the remote and destination branch. Verify the confirmation address; push uses
Git's push URLs, which may differ from fetch URLs.

- Fetch updates remote references without merging working files.
- Pull is fast-forward only. Modified/untracked files and diverged histories block it.
  No automatic stash, rebase or conflict resolution is performed.
- Push sends current HEAD to the specified remote branch, without force. Authentication
  and permission failures are reported from Git, not treated as success.

Git I/O runs on a worker thread. Repeated actions and closing are blocked while busy.
Operations time out after 120 seconds; a timeout can have an unknown remote outcome.
Refresh/verify before retrying. Clone, branch switching, conflict editing, history
rewriting and force operations are not included; use Git itself when needed.

## Test boundaries

Tests use real Git, real Tk button callbacks and disposable repositories. Local bare
repositories simulate remotes for commit/push/pull, dirty worktrees, divergence and
rejected pushes. Your production repository is never used for trial uploads.
Missing-Git/cancel-install paths are simulated, not a clean Windows installation test.
Real GitHub login, proxy environments and administrator installation need their own validation.
